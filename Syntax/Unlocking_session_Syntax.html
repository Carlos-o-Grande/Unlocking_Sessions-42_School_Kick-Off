The Byte & Types in C

~7 min
Slide 04 Live Demo - IDE

Nibbles & hex - 0x42 is not 42

S04

A nibble is 4 bits. Two nibbles make a byte. Each nibble maps to exactly one hex digit.
>> shifts bits right, & keeps only the bits set in both - these are bitwise operators: they work on each bit separately.

hex literal: 0x42
0100  0010 upper nibble  lower nibble
4 × 16 + 2 × 1 = 66 decimal 
▶ Step through⚙ Compile & run#include <stdio.h>
int     main(void)
{
    int     n;
    int     upper;
    int     lower;

    n = 0x42;                   // hex literal - decimal value is 66, not 42!
    upper = (n >> 4) & 0x0F;    // shift right 4, mask - upper nibble
    lower = n & 0x0F;            // mask lower 4 bits - lower nibble
    printf("hex:          0x%02X\n", n);      // 0x42
    printf("decimal:      %d\n", n);           // 66
    printf("upper nibble: %d\n", upper);        // 4
    printf("lower nibble: %d\n", lower);        // 2
    return (0);
}
Hex is a compact way to write binary - one hex digit per nibble. This is why memory addresses and bitmasks are always shown in hex.

On the nibble demo (S04): "The school is called 42. But if you write 0x42 in C - the hex literal - what does it equal?" Pause. Show the nibble breakdown. Upper nibble 4, lower nibble 2, total 4×16+2 = 66. Compile and run to confirm. This is a memorable moment that connects the school name to a real binary concept.

The >> shift and & 0x0F mask are bitwise operations - you don't need to teach them, just show the pattern and say "this extracts the upper or lower 4 bits".

"Why do you think memory addresses are always shown in hex rather than decimal?" - each byte = exactly 2 hex digits. Much more compact for raw memory values.

Types - the compiler's memory contract

S05

A type tells the compiler: how many bytes to read and how to interpret them. That is all a type is.

Type Size (64-bit) Range / Notes
char 1 byte −128 → 127  |  unsigned: 0 → 255  |  holds one character  |  plain char may be signed or unsigned, depending on the platform
int 4 bytes −2,147,483,648 → 2,147,483,647
long 8 bytes ~±9.2 × 10¹⁸
float 4 bytes ~7 significant decimal digits
double 8 bytes ~15 significant decimal digits
size_t 8 bytes Unsigned · safe for sizes & indices · platform-adapted 
▶ Step through⚙ Compile & runint    a = 7;
int    b = 2;
float  result;

result = a / b;           // int / int = int - result is 3.0, not 3.5
result = (float)a / b;    // explicit cast - result is 3.5
int ÷ int = int. Always. The decimal is silently discarded. One of the most common silent bugs in C.

On types (S05): The core idea: types are a contract with the compiler. Without them, the compiler has no idea how many bytes to read at a given address.

On the implicit conversion demo: Type it live. The result being 3.0 surprises people every single time. The fix - explicit cast - is the lesson.

Likely Follow-up

"Is int always 4 bytes?"

On all 42 school machines (64-bit Linux), yes. The C standard only guarantees a minimum. That's why stdint.h provides int32_t and uint64_t for guaranteed-size needs.

Types control what the compiler reads. Flags control what the compiler tells you when something looks wrong.

Signed vs unsigned - same bits, two readings

S06

The type doesn't change the bits in memory - it changes how they are read.

Same bits, two readings - the type decides
▶ Step through⚙ Compile & runsigned char    s;
unsigned char  u;

s = -3;
u = s;                      // same 8 bits
printf("%d %d\n", s, u);    // -3 253
Same 8 bits, two ranges
s = 1111 1101   signed    −3

signed char     −128 → 127
unsigned char      0 → 255
Negative numbers are stored in two's complement; one's complement was an earlier attempt. Study both: why does signed char stop at 127, while unsigned char reaches 255 with the same 8 bits?

Optional - skip it if you're short on time. Spend it on the demo: the bits never change, the type decides how they are read. Point back at the ranges in S05.

Name one's and two's complement, don't explain them - that's their research.

Likely Follow-up

"What happens if I store 200 in a signed char?"

The bits wrap: it reads back as −56 (200 − 256). Whether you're warned depends on the compiler - c = 200; compiles silently with gcc and -Wall -Wextra -Werror, while clang stops it with -Wconstant-conversion.

Compiler Flags & Makefile

~6 min
Slide 07 Table

-Wall -Wextra -Werror - your first line of defence

S07

These three flags are mandatory at 42. Together they turn suspicious code into compile errors.

Flag What it catches
-Wall Unused variables · missing return · assignment in condition if (x = 5)
Precedence a & b == 0 - read as a & (b == 0)
- the standard set of "probably a bug" warnings
-Wextra Signed/unsigned comparison · unused parameters
- goes beyond -Wall to catch subtler issues
-Werror Treats every warning as a compile error.
Code does not compile if it has any warning. No exceptions.

Not caught by any of the three: shadowed variables - an inner x hiding an outer x compiles silently. Only -Wshadow warns. → S16 - Scope

Your Makefile may add other flags, as long as they don't switch off any of the three above.

Flag What it does
-g Adds debug info - the debugger can stop at a source line and show variable names
- without it, gdb says "No symbol table is loaded"
-O0 … -O3 Optimization level. -O0 (default): runs as written · -O2: faster, but code is reordered and removed
- debug with -O0 -g: optimized code shows the debugger wrong values or <optimized out>
The flags don't make your code better - they make the compiler louder when your code is suspicious. That loudness is a feature, not an obstacle.
Slide 08 Code

Makefile - the build contract

S08

Add source filenames to FILES to compile multi-file programs. This is the minimum useful Makefile.

CC     = cc
CFLAGS = -Wall -Wextra -Werror
NAME   = program
FILES  = main.c

all:
	$(CC) $(CFLAGS) $(FILES) -o $(NAME)

clean:
	rm -f $(NAME)

fclean: clean

re: fclean all

.PHONY: all clean fclean re
  • make - compile. make re - recompile from scratch
  • Add more sources to FILES separated by spaces - immediate multi-file support
  • fclean and clean both remove the binary - no object files in this setup
  • Extend with OBJS and pattern rules when your project grows
  • Minimal and working, but not Norm-compliant (no $(NAME) rule, it relinks every time) - making it compliant is up to you
The CFLAGS are already set to the 42 mandatory flags. Your code compiles with the same strictness every time, on every machine.

Students sometimes disable warnings to make their code compile. This slide explains why that's backwards - warnings are telling you something. -Werror forces you to listen.

"Has anyone had a program compile successfully and then crash at runtime - with no warnings? What does that tell you about what warnings catch?" - most hands go up. Answer: warnings catch things that look suspicious at compile time, not everything that goes wrong at runtime.

On the Makefile (S08): Explain each variable. Show it working with the nibble demo code from S04 - make, then run the program. The simplicity is the point. Add a second .c file to FILES live to show it still works.

Likely Follow-up

"Can I silence a specific warning?"

Yes - with -Wno-warning-name. At 42, the subject flags are fixed and you shouldn't silence them. In real-world code you sometimes suppress known-intentional patterns. For now: if the compiler warns about it, fix it.

The flags will catch many boolean and assignment mistakes before they reach runtime. Let's look at those patterns now.

Slide 10 Code

Short-circuit evaluation

S10
  • && stops at the first false - right side never evaluates if left is false
  • || stops at the first true - right side never evaluates if left is true 
▶ Step through⚙ Compile & runif (ptr->value == 42)          // crash if ptr is NULL - reads from address 0
    do_something();

if (ptr && ptr->value == 42)   // safe - right side only runs if ptr is not NULL
    do_something();
Short-circuit is a pattern, not a trick. Always check a pointer is non-NULL before dereferencing it.
Slide 11 Code

The = vs == trap

S11

= assigns, == compares. Mixing them up inside a condition is a silent bug: without the flags it compiles and always takes the branch.

▶ Step through⚙ Compile & run⚙ Run without flagsint   x;

x = 0;
if (x = 5)    // assigns 5 to x, evaluates x (truthy) - always runs
    ...
if (x == 5)   // compares x to 5 - what you meant
    ...
  • -Wall catches it: suggest parentheses around assignment used as truth value
  • Silencing it with if ((x = 5)) still breaks the Norm - assignment inside a condition is forbidden
Read = as "becomes" and == as "is equal to". If a condition reads "x becomes 5", it's the bug.

▶ Step through⚙ Compile & runa & b == 0    // becomes: a & (b == 0)  - equality binds tighter than &

Slide 13 Code

Precedence ≠ evaluation order

S13

Two different questions about the same expression: how is it grouped, and what runs first?

Precedence → grouping

f() + g() * 3 is always read as f() + (g() * 3)
* binds tighter than +: the multiply is grouped first.

Evaluation order → what runs first

Which call runs first, f() or g()?
C leaves it to the compiler - and they disagree:

▶ Step through⚙ Compile & runint   f(void);      // prints "f ", returns 1
int   g(void);      // prints "g ", returns 2
int   show(int a, int b);

show(f(), g());     // which name prints first?
// gcc 16:  g f       clang 22:  f g
  • Only &&, ||, ?: and , guarantee their left side runs first - the short-circuit from S10
  • Changing one variable twice in an expression is undefined: i = i++ + 1; - the 42 flags reject it in both compilers
Precedence tells you how an expression is grouped, never what runs first. Keep one side effect per expression.

On truth tables (S09): Before explaining, point at the orange-striped row (A=1, B=1). "Look at the same-coloured row across all six tables - when both inputs are 1, what does each operation give?" Let them read back.

"Look at the XOR table - when is XOR false? What do those rows have in common?" - only the rows where A equals B. XOR means "they're different." Useful in conditionals when you want exactly one of two conditions true.

On NAND and NOR (De Morgan section): "NAND is AND with the output flipped. NOR is OR with the output flipped. De Morgan's law tells us how to rewrite them - distribute the NOT and flip the operator. This comes up when you want to simplify a negated compound condition." Show the equivalence on paper if helpful.

On short-circuit (S10): The ptr example is the key. If ptr is NULL (0), the && short-circuits: right side never evaluates, no crash. This is why && and || are designed this way - it's not an accident.

On = vs == (S11): Use the ⚙ Compile & run button first - the flags stop it. Then ⚙ Run without flags to show the branch always taken.

"Walk me through what happens step by step when C evaluates if (x = 5)." - assign 5 to x, evaluate x (5 is nonzero = true), branch always taken. -Wall produces: warning: suggest parentheses around assignment used as truth value.

On the precedence table (S12): Don't read it aloud. Use it as visual reference. Walk through each trap example. On *ptr++: "postfix ++ binds before *, so the pointer advances - not the dereferenced value." They'll use this pattern in the defensive programming section.

Likely Follow-up

"Does C have a bool type?"

Yes - via #include <stdbool.h> in C99, giving bool, true, false. Most 42 code uses int as booleans. The logic is identical: 0 = false, nonzero = true.

On evaluation order (S13): Keep it to the two questions: the table answers "how is it grouped", never "what runs first".

"show(f(), g()) - which name prints first?" Let them guess, then ⚙ Compile & run: Compiler Explorer opens two run panes - gcc 16.2 prints g f, clang 22.1 prints f g. Same code, same flags, different order.

Likely Follow-up

"So one of the compilers is wrong?"

Neither. C leaves the order to the compiler. The bug is code whose result depends on it - call side-effect functions on separate lines when order matters.

Boolean logic at work - adding and multiplying

~5 min · optional
Slide 14 Code

How the CPU adds - XOR and AND

S14

The AND and XOR from the truth tables, applied to every bit of a number at once - that's why &, ^ and | are called bitwise operators. XOR gives the sum of two bits, AND shows where a carry is born.

5 + 3 without using +
▶ Step through⚙ Compile & rununsigned int  a;
unsigned int  b;
unsigned int  carry;

a = 0x5;                  // 0101
b = 0x3;                  // 0011
while (b != 0)
{
    carry = a & b;        // 1 + 1 → a carry is born
    a = a ^ b;            // sum, ignoring carries
    b = carry << 1;       // carry moves one place left
}
// a = 1000 (8)
Each row: a ^ b → new a · (a & b) << 1 → new b
      a      b     a ^ b  (a & b) << 1
1   0101   0011    0110     0010
2   0110   0010    0100     0100
3   0100   0100    0000     1000
4   0000   1000    1000     0000  stop

                   a = 1000 (8) ✓
Inside the CPU, the adder is built from the same XOR and AND gates - this loop does the same work in software.

On adding (S14): Go back to the S09 tables. 1 XOR 1 = 0 and 1 AND 1 = 1 - that is 1 + 1 = 10: write 0, carry 1. XOR gives the digit, AND gives the carry, the shift moves the carry to the next column. Walk the trace one row at a time.

Reveal rows 1 and 2, then ask: "What are a and b on row 3?" - 0110 ^ 0010 = 0100, and (0110 & 0010) << 1 = 0100. "When does the loop stop?" - when there is no carry left (b == 0).

Slide 15 Code

How the CPU multiplies - shift and add

S15

Shifting left one place multiplies by 2: 0011 (3) << 1 = 0110 (6). For every 1 bit in b, add the matching shifted copy of a.

3 × 5 without using *
▶ Step through⚙ Compile & rununsigned int  a;
unsigned int  b;
unsigned int  r;

a = 0x3;                  // 0011
b = 0x5;                  // 0101
r = 0;
while (b != 0)
{
    if (b & 1)            // last bit of b is 1?
        r += a;           // then add a
    a <<= 1;              // a × 2
    b >>= 1;              // move to the next bit of b
}
// r = 1111 (15)
Each row: add a if b & 1, then a << 1, b >> 1
      b    b & 1    a     r
1   0101     1    0011   0000 + 0011 = 0011
2   0010     0    0110   0011
3   0001     1    1100   0011 + 1100 = 1111
4   0000   stop

                 r = 1111 (15) ✓
Same method as long multiplication by hand - in binary each digit is 0 or 1, so every step is either "add" or "skip".

On multiplying (S15): Do 3 × 5 as decimal long multiplication on the board first, then point at the code: each digit of b is 0 or 1, so each row is "add a" or "skip". a <<= 1 is the next row of long multiplication, shifted one place left.

Scope & Variable Lifetime

~5 min
Slide 16 Visual

Scope - { } is a life boundary

S16
▶ Step through⚙ Compile & run int main(void) { int x = 10;                          BORN { int x = 99;                     BORN SHADOWS outer x printf("%d\n", x);   // prints 99 }                                    inner x DEAD printf("%d\n", x);    // prints 10 }
  • A variable lives from its declaration to the closing }
  • Shadowing: inner name hides outer - outer still exists, just unreachable. Compiles silently with -Wall -Wextra -Werror - only -Wshadow warns (S07)
  • 42 norm: declare all variables at the top of the function - no nested declarations 
▶ Step through⚙ Compile & runint   count_calls(void)
{
    static int  calls;

    calls++;
    return (calls);
}
// 1st call: 1, then 2, then 3
static - same scope, longer life

A static local is still only visible inside its function, but it lives for the whole program: it starts at 0 and keeps its value between calls.

The norm rule isn't arbitrary. Declarations at the top make the entire variable set visible at a glance.
Slide 17 Live Demo

Uninitialized variables - reading garbage

S17
▶ Step through⚙ Compile & run⚙ Run without flagsint   x;
printf("%d\n", x);   // undefined behaviour - prints whatever was there before

int   x;
x = 0;               // explicit initialization - predictable

int   arr[5];
ft_memset(arr, 0, sizeof(arr));  // zero-initialize a whole array
  • An uninitialized local variable holds whatever memory happened to be there
  • C makes no guarantee - the value may differ on every run, every machine
  • Habit: initialize to 0 when you declare, even if you will assign later
  • With -Wall -Wextra -Werror this doesn't compile - 'x' is used uninitialized
The 42 flags stop this before it runs. Without them it compiles silently and prints whatever was in memory - a different value on different runs. That is the behaviour named "undefined".

On scope (S16): Walk through line by line. "We enter the outer block. x=10 is born. Inner block opens. A new x=99 is born - it hides the outer. We see 99. Inner block closes - inner x dies. We're back to 10." Draw nested boxes if needed.

"If I declare a variable inside a while loop body - what happens to it on the next iteration?" In norm-compliant code this can't happen, but the concept of lifetime still applies at function scope.

On uninitialized vars (S17): Click ⚙ Compile & run first: with the 42 flags the compiler refuses it ('x' is used uninitialized). Then ▶ Step through: x shows as ? and it stops at the printf with an "uninitialised value" error. To show the garbage itself, compile it live without flags (cc s12_uninitialized.c) and run it a few times - the value can change between runs (gcc gave -1025092928, then 0). This visual demonstration is more memorable than any explanation. After: "Where exactly does that variable live in memory?" - let answers come. "Stack" is correct. "That's the next session."

Loops

~6 min
Slide 18 Code

While - the only loop you write at 42

S18
▶ Step through⚙ Compile & runint   i;

i = 0;                       // 1. init      - before the loop
while (i < 5)                // 2. condition - tested before each iteration
{
    printf("%d\n", i);        // 3. body      - what you want to repeat
    i++;                      // 4. increment - move toward the exit condition
}                             // jumps back to 2
  • for exists and is the same machine - norm forbids it. Converting: step 1 goes before, step 4 goes to the body's end. Done.
  • Off-by-one: i < 5 → indices 0,1,2,3,4 (correct for a 5-element array). i <= 5 → 6 iterations, last is out of bounds.
  • Missing step 4 → infinite loop. The condition never changes.
  • Also forbidden by norm: for do…while
Every while loop has four parts. If one is missing - you have a bug or an infinite loop. Always ask: "What changes to eventually make the condition false?"
Slide 19 Live Demo

Nested loops - name your variables for the context

S19
▶ Step through⚙ Compile & runint   row;
int   col;

row = 0;
while (row < 3)                // outer: controls which row we are on
{
    col = 0;
    while (col < 4)             // inner: runs completely for each row
    {
        printf("[%d,%d] ", row, col);
        col++;
    }
    printf("\n");
    row++;
}
  • Inner loop executes completely for each outer step: 3 × 4 = 12 total
  • row and col - not i and j. The name tells you which dimension you're in
  • In geometric code: x and y are better still - name what the value means
  • Classic bug: forgetting col = 0 inside the outer loop - demo this deliberately
When operating in two dimensions - grid, matrix, 2D space - your variable names should reflect those dimensions. i and j tell you nothing. row and col tell you everything.

On the while anatomy (S18): Number each part as you speak. Students know how to write loops - naming the four parts makes the structure explicit. "Which of the four parts is missing?" is a more useful debugging question than "what's wrong?"

On for: 20 seconds. "It exists. You'll see it everywhere. Norm forbids it. The conversion is one move - figure it out yourself."

"For a 5-element array - which is correct: i < 5 or i <= 5? Tell me the index of the last element first." Indices go 0 through 4. i < 5 is correct. i <= 5 reaches index 5 - outside the array.

On nested loops (S19): Build incrementally in the IDE. First outer loop printing just the row number. Then add inner loop. Then deliberately remove col = 0 inside the outer loop and run it. Show the bug. Restore. Students remember witnessed bugs.

On naming: make it natural, not a rule. "I could write i and j here - but look at the printf. If the outer variable is called row, I don't have to think about which loop is which while I'm reading."

int     pixel_x;      // not i
int     pixel_y;      // not j
int     row;          // not i - even for simple loops
int     col;          // not j

// len is universal - always understood
size_t  len;
  • 42 norm: snake_case for functions, variables and types; UPPER_CASE for macros; no camelCase
  • A name should answer: what does this hold or what does this do
  • If you need a comment to explain a variable name - rename the variable instead
The person reading your code at 2am debugging a segfault is you. Name things so that person can work without rereading every function.

This is about intention, not rules. The audience already writes code - this is about writing code that communicates.

"If a function is called process - what does it do?" They'll say "we don't know." Follow up: "What if it's called validate_email?" The contrast makes the principle obvious without a lecture.

The is_ / has_ prefix for booleans is a widely used convention. It makes conditions read like English: if (is_valid), while (has_more_tokens).

The "if you need a comment to explain the name - rename it" line usually gets a reaction. Let it land before moving on.

len is a universally understood abbreviation - there's no ambiguity. Don't spell it out as length_of_string; that's noise. Don't abbreviate further to l; that's a single letter with no meaning.

Good names prevent bugs. Defensive programming catches the bugs that names can't prevent.

Defensive Programming

~10 min
Slide 21 Code

Guard clauses - handle bad cases first

S21

Defensive programming: write code that handles what shouldn't happen - before it does.

Three levels of nesting
▶ Step through⚙ Compile & runint process(char *s, int len)
{
    int   result;

    result = 0;
    if (s)
    {
        if (len > 0)
        {
            // work lives 3 levels deep
            result = 1;
        }
    }
    return (result);
}
Flat - one level
▶ Step through⚙ Compile & runint process(char *s, int len)
{
    if (!s || len <= 0)
        return (0);
    // happy path - no nesting
    return (1);
}

Invert the bad conditions. Return early. Keep the main logic at the shallowest indentation level.

Every level of nesting is a place bugs hide. Flat code is readable code. Readable code is maintainable code.

Slide 23 Code

Header guards & const - systematic protection

S23
Header guard - prevent double inclusion
#ifndef MYPROJECT_H
# define MYPROJECT_H

typedef struct s_point
{
    int  x;
    int  y;
}   t_point;

int   my_function(void);

#endif

Without this: a header included twice defines t_point twice → redefinition error.

const - making intent visible
const char  *s;
// data is immutable, pointer can change

char  *const s;
// pointer is immutable, data can change

size_t  ft_strlen(const char *str);
// promise: I will not modify your string
Header guards are the canonical C defensive pattern - every .h file you write should have one. const is a promise you make to the compiler and to whoever calls your function.
Slide 24 - Approach A Live Demo

Iterating without int i - approach A: sizeof

S24
▶ Step through⚙ Compile & runint     arr[] = {10, 20, 30, 40, 50};
size_t  len;
int     *ptr;

// sizeof(arr)    = 5 x 4 = 20 bytes (total array)
// sizeof(arr[0]) = 4 bytes     (one element)
// 20 / 4         = 5           (number of elements)
len = sizeof(arr) / sizeof(arr[0]);

ptr = arr;
while (ptr < arr + len)
{
    printf("%d\n", *ptr);
    ptr++;
}
  • The pointer is the iterator - no index variable needed
  • ptr++ advances by sizeof(int) bytes - it knows the type
  • ⚠️ This breaks if you pass arr to a function - sizeof returns the pointer size, not the array size. This has a name: pointer decay.
sizeof / sizeof works only when the array is declared in the same scope. Once passed to a function, the size information is gone. That mechanism is the next session's opening.
Slide 25 - Approach B Live Demo

Iterating without int i - approach B: pointer as iterator

S25
▶ Step through⚙ Compile & run// Works when the array has a sentinel - a value that marks the end
int   arr[] = {10, 20, 30, 40, 50, 0};   // 0 = end marker
int   *ptr;

ptr = arr;
while (*ptr)
{
    printf("%d\n", *ptr);
    ptr++;
}

// argv is already NULL-terminated - same pattern, no design needed
char  **arg;

arg = argv + 1;    // skip program name
while (*arg)
{
    printf("%s\n", *arg);
    arg++;
}
  • Strings already use this - '\0' is a sentinel. Strings are not special; they are char arrays with a contract
  • You need to design the contract: what value means "end"?
  • argv is a real example they have used - NULL-terminated array of char pointers
The sentinel approach requires a contract. Once you have one, the pointer drives itself - no index, no counter, no sizeof.

On guard clauses (S21): Show both side by side in the IDE. Ask: "Which would you rather debug at 2am?" The flat version always wins. The key move: invert the bad condition, return immediately, keep the work at the shallowest level.

"Give me a concrete scenario where not checking for NULL before using a pointer causes a problem - what exactly happens at runtime?" Guide toward: segmentation fault (SIGSEGV). You are writing to or reading from memory you do not own. The OS kills the process.

On the muggle slide (S22): Let the joke land before moving to the code. The "change it in one place" argument is the practical reason. Spend 30 seconds on the why, not the what.

On header guards (S23): Quick scenario: main.c includes a.h and b.h, and both of those include myproject.h. Without guards, myproject.h is pasted into main.c twice, so t_point is defined twice - redefinition error. With the guard, the second include is a no-op. Prototypes alone can repeat safely; it's definitions (structs, typedefs) that clash. Every .h file you write should have one; the Norm names the guard after the file: ft_foo.h → FT_FOO_H.

On const (S23): const left of * means data is const. const right of * means pointer is const. Function parameters marked const char * are a promise: "I will not modify your string." The compiler enforces that promise.

On sizeof approach (S24): Walk through the math on screen.

On sentinel approach (S25): The loop body can shrink to one line: printf("%d\n", *ptr++); prints the value, then moves the pointer - the *ptr++ from the precedence slide (S12).

Connect to ft_strlen: they wrote while (str[i] != '\0') i++; - this is just while (*str) str++;. Same logic, pointer-driven. argv is a real example they have used.

Likely Follow-up

"What is the difference between NULL, '\0', and 0?"

In C all three compare equal - they are all zero. NULL is (void*)0 for pointers. '\0' is the null byte for string terminators. 0 is the integer zero. Using the right one communicates intent, even if the behaviour is identical.

You can write, defend, and iterate over C code. The last skill: reading a declaration you have never seen before.

Slide 26 Visual

The inside-out, right-then-left rule

S26

Start at the identifier. Go right first, then left, jump out of parentheses and repeat.
Read * as "pointer to", ( ) after a name as "function", [ ] as "array of".

char  *(*f)(int, char *)

1
Start at f
2
Go right → hit ). Go left → *.  declare f as pointer to
3
Escape ( ). Go right → (int, char *).  function (int, pointer to char)
4
Go left → char *.  returning pointer to char
declare f as pointer to function (int, pointer to char) returning pointer to char
You won't write declarations like this often. But you will read them in headers, man pages, and other people's code. Being able to parse them calmly is a superpower.
Slide 27 Live Demo - cdecl.org

Practice - and validate at cdecl.org

S27
// Read these before I reveal - right-then-left from the name

int   (*arr)[5]
// arr is a pointer to array 5 of int

const char  *s
// s is a pointer to const char  (data immutable, pointer movable)

char  *const s
// s is a const pointer to char  (pointer immutable, data mutable)

Navigate live to cdecl.org - type a declaration, get plain English. Use it as validation, not as a crutch.

  • const left of * → data is const
  • const right of * → pointer is const
  • The position relative to the star is the rule
const left of * = data is const. const right of * = pointer is const.

Before showing the answer (S26): Put the declaration on screen and ask someone to attempt a reading. "Don't be afraid to be wrong - what do you think the outer star is doing?" The most common wrong answer: "f is a function returning a pointer to char" - it misses that f itself is a pointer, to a function. The right framing: the parentheses around (*f) group the star with f, making f itself the pointer. cdecl.org reads it as "declare f as pointer to function (int, pointer to char) returning pointer to char".

"Before I walk through it - tell me what you think the parentheses around (*f) are doing here. Why are they there?" Without them, char **f(int, char *) would be a function returning char ** (pointer to pointer to char), not a pointer to a function.

On cdecl.org (S27): Navigate live. Type the declarations in order. Let students read before you reveal. If internet is unavailable, the method stands on its own - skip the site.

Likely Follow-up

"When would I use a function pointer?"

Callbacks - passing a function as an argument. ft_lstmap takes a function pointer to apply to each list node. qsort() takes a comparator. Anywhere you want to parameterise behaviour without if/else chains. You will use this throughout your 42 projects.

Likely Follow-up

"Is there a rule for where to put const - before or after the type?"

const int * and int const * are identical. What matters is position relative to the star. Const left of star = data const. Const right of star = pointer const.
